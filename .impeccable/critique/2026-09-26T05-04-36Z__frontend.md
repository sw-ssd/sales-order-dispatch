## Design Specificity Verdict

**中度 authored：骨架專屬，肌理通用。**

**LLM 判定（未看偵測器輸出前的獨立判斷）**：專屬的部分是真的——「控制室」定位、Pallet Clay 單一強調色（亮度刻意壓到 4.5:1）、用語全部沿用現場慣稱（派車、揀貨、對點、分切、車次）、依 `delivery_sequence` 的車次欄看板、`PlanBanner` 這個把訂閱狀態釘在每頁固定位置的 signature 元件。這些換到任何其他 admin 產品都不成立。

但列表頁的肌理是 category-interchangeable 的：orders／customers／printing 全是同一個「標題＋muted 篩選帶＋nowrap 表格＋行內文字動作」模板，首頁是三張大數字卡＋六顆快速連結。蓋掉 logo 後與任何 Tailkit 後台難以區分。**結論：設計系統層有清晰觀點，頁面構圖層停止了思考。**

**Deterministic scan**：CLI 掃 `frontend/index.html frontend/src` 僅 1 筆 finding（`overused-font`：Inter，`index.css:197`，warning）。

**Visual overlays**：注入成功。標記為 `[Human]` 的瀏覽器分頁目前停在 `/orders`，畫面上有偵測器覆蓋層（`.impeccable-overlay`／`.impeccable-banner`）。跨 5 頁（`/`、`/orders`、`/dispatch`、`/customers`、`/printing`）的 console 回報：

- `overused-font` — Primary font: Inter（100% 的文字），每頁都有
- `skipped-heading` — `<h1>多公司訂出貨系統` 後接 `<h3>今日待出貨`（缺 h2），首頁
- `layout-transition` — `transition: width`（側欄寬度過場），每頁都有
- `nested-cards` — 卡片包卡片，首頁與列印頁
- `edge-flush-cards` — 1 個卡片貼齊 `div.relative.w-full.overflow-x-auto` 左緣（表頭 `th.bg-muted`）與派車看板的車次欄

**誤判與真陽性辨識**：

- `edge-flush-cards` 是**真陽性但我們接受**：表格貼齊卡片左緣就是密集表格的設計決定（`DESIGN.md` 的 Full-Bleed Content Rule），不是缺陷。
- `nested-cards` 首頁為真（統計卡在容器內），列印頁為誤判（那是表格在卡片內）。
- `layout-transition` 是**誤判**：`transition: width` 在側欄是刻意的 200ms 過場，不是版面位移缺陷——但它確實指出了側欄收斂會觸發版面重排，在低階機器上可能看見抖動，值得一次實測。
- `skipped-heading` 是**真陽性**：`CardTitle` 硬綁 `<h3>`，首頁 `h1` 之下直接跳 `h3`。這是元件層的結構限制，不是單頁疏忽。
- `overused-font` 的判定在**這個產品上是刻意成立**的：內部工具、中文為主、Inter 只負責拉丁字與數字；換字體的收益遠低於工程風險。列為已知接受項。
- 偵測器**沒抓到**的、由 Assessment A 找到的：作廢失敗訊息被遮罩吞掉（狀態／錯誤恢復）、列印要手打車次 ID（辨識負擔）、`window.confirm` 與 Dialog 並存（一致性）——這三項都需要理解流程語意，不是靜態規則抓得到的。

**本輪順帶修正的兩個文件錯誤**（評測過程發現，已改）：

1. `DESIGN.md` 原寫「備料黃＝待處理、調度藍＝處理中」，與實作相反。實作是**訂單** `pending` 配藍、`processing` 配黃，而**退貨／使用者**的 `pending` 配黃——兩份都是現行事實。已改為記述實作並標明這處不一致，避免下一頁跟著錯的那份走。

## Overall Impression

這是一套**知道自己不是展示品**的介面：克制、密集、用語正確，派車看板的部分失敗回饋與 `PlanBanner` 的「不吵契約」是真正成熟的設計判斷。

最大的機會不在美化，而在**高頻作業路徑上的摩擦點**：列印要背內部 ID、破壞性動作沒有分級、失敗訊息被遮罩吞掉。三件事都跟視覺無關，全是流程與文案問題——這也說明了為什麼它們能在一套整齊的設計系統底下存活這麼久。

## What's Working

1. **派車看板的非拖曳指派路徑**（`DispatchPage.tsx:394-412`）：HTML5 拖放在 iPad 與純鍵盤不可用，卡片內嵌「指派到車次…」下拉作為語意等價入口，且註解把理由寫清楚。把無障礙當功能而非合規，這在內部工具裡少見。
2. **`StatCard` 的「— vs 0」語義**（`DashboardPage.tsx:40-64`）：查詢失敗顯示「—」而非 0。「查不到」與「真的沒有」在營運判斷上完全相反，這個區分被實作出來並附上理由。
3. **`PlanBanner` 的不吵契約**：只在 80/90% 用量或試用將到期時出現、載入失敗靜默、多筆提示取最嚴重者。通知設計裡最難的「什麼時候不說話」被寫成契約。

## Priority Issues

### [P1] 作廢的錯誤訊息顯示在被遮罩蓋住的頁面橫幅
- **問題**：`OrdersPage.tsx:494-505` 的 `submitVoid` 在「未填原因」與 `voidOrder` 失敗時都寫入 `actionError`，而它只渲染在頁首 `bannerError`（`:551`）。此時作廢 Dialog 仍開著、`bg-foreground/75` 遮罩蓋住整頁，使用者在對話框內看不到任何回饋。
- **為什麼重要**：作廢是**終態**操作。失敗無回饋＝重複點擊或誤關視窗，而終態操作的誤判代價不可逆。
- **修法**：比照 `PrintPage` 的 `serverError`，在 Dialog 內渲染 dialog-scoped 錯誤帶；`actionError` 只保留給非 modal 的行內動作。
- **建議命令**：`$impeccable harden`

### [P1] 列印流程要求手打內部車次 ID
- **問題**：`PrintPage.tsx:508-519` 的正式列印 Dialog 把「車次 *」做成自由輸入框（placeholder「車次 ID」），列表篩選也是同一個文字框。但全站其他畫面（派車看板、列印紀錄表格）只顯示車次名稱與代碼（`1車 (R01)`、`#55`），使用者無處可查這個內部 ID。
- **為什麼重要**：列印是倉庫端最高頻的作業，卻要憑記憶輸入看不見的識別碼；打錯只能等後端 `InvalidArgument`。這是整條現場旅程最深的谷。
- **修法**：改為車次下拉（資料源同派車頁的 `activeRoutes`），篩選列同改；`#55` 這類顯示值一併改為「代碼＋名稱」。
- **建議命令**：`$impeccable clarify`

### [P2] 破壞性動作沒有視覺分級，且兩套確認語言並存
- **問題**：`pending` 列的操作欄是 詳情／編輯（主色）＋**取消／刪除（皆 `text-destructive`）**；全庫 23 處用 `window.confirm`（`OrdersPage.tsx:476`、`CustomersPage`、`masters/*`、`UsersPage`、`ReturnsPage`×3…），只有作廢走設計系統 Dialog。
- **為什麼重要**：「取消」是狀態機的正常轉移（可再補單）、「刪除」是主檔級破壞操作，兩者視覺不可分且相距 12px。`window.confirm` 是瀏覽器 chrome 樣式、不吃 token、放不下影響範圍說明，與控制室的克制語言直接衝突。
- **修法**：狀態機轉移（取消／完成）降為中性色，紅色只保留給刪除／作廢；確認流程統一收進 Dialog，並帶一行影響範圍（例：「此單已在車次 R01 順位 3」）。
- **建議命令**：`$impeccable distill`

### [P2] 系統語言洩漏到作業語言
- **問題**：`PrintPage.tsx:324`「預覽不限狀態；正式列印限 processing」把後端列舉值寫進面向倉管人員的文案；同頁列印人欄顯示 `#8`（內部 user id）；訂單來源欄顯示裸代碼 `W`。
- **為什麼重要**：違反全站 zh-Hant 與「用語沿用現場慣稱」的承諾；列舉值一旦隨狀態機改名就會變成錯誤文案。
- **修法**：全部走翻譯層（`STATUS_LABELS` 這類）；列印人改顯示姓名（或暫以「—」）；來源改為可讀標籤。
- **建議命令**：`$impeccable clarify`

### [P3] 狀態色語意與時間格式在頁面間漂移
- **問題**：訂單 `pending`＝藍、`processing`＝黃，但退貨與使用者頁 `pending`＝黃（`ReturnsPage.tsx:72`、`UsersPage.tsx:69`）；`CustomersPage.tsx:155-158` 的建立時間直接輸出原始 RFC3339（截圖可見 `2026-09-25T01:43:09+08:00`），訂單頁同欄位有格式化。
- **為什麼重要**：狀態色是每天掃視的訊號，同一語意兩種顏色會讓「藍＝什麼」失效。時間格式不一致讓最常用的客戶主檔看起來最粗糙。
- **修法**：狀態→語意色的對照表抽成共用模組並定案（含 pending 到底藍或黃）；建立時間抽共用 formatter。
- **建議命令**：`$impeccable polish`

- `CardTitle` 硬綁 `<h3>`，導致首頁 `h1 → h3` 跳級（偵測器 `skipped-heading` 真陽性）。要修得改元件 API 或補 `h2`。

## Questions to Consider

1. 「含已刪除」出現在每一個主檔頁的篩選列——它服務的是會計式追溯，還是把一年用三次的「還原」抬到了與「查詢」同等的視覺地位？
2. 派車看板的車次欄固定寬：若某租戶有 12 個車次，看板該繼續橫捲，還是承認「超過 N 欄就不再是看板」、需要另一種密度模式？
3. 「一頁一動作」原則在訂單列表頁成立了嗎？同一列最多四個動作、兩個紅色——這條原則約束了頁面主按鈕，卻沒約束列級動作數。
4. `PlanBanner` 選擇「不吵」、`Topbar` 選擇「不說我是誰」——這套系統的狀態可見性策略是刻意最小化。當租戶從 1 家變 50 家、角色從 3 種變 7 種，第一個該放棄的是哪一個？
