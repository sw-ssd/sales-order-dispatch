## Design Specificity Verdict

**在「形」上通用，在「動」上專屬。**

真正 product-specific 的表面（換到別的產品就說不通）：派車看板（車次為欄、未指派獨立欄、`version` 樂觀鎖拖放、批次確認、日期即整頁主軸、串流只當失效提示）；四種紙本單據的列印歷史（首印／重印語意、重印原因常駐、`download_url` 直連）；權限矩陣（13×8 resource×action 網格，含 `sales_order×cancel {status:pending}` 這種條件式規則）；訂單明細的單位換算與別名（「同一商品在各部門各有名稱」這個定位的落地）；退貨刻意沒有建單入口——用「不做什麼」表態。

category-interchangeable 的部分：整個 shell（側欄 4 群 19 項＋頂列＋單一內容柱）與**所有清單頁的骨幹**——頁首 h1＋副標、`bg-muted` 篩選帶、一張 Card 內含篩選→表格→分頁、對話框。`DashboardPage.tsx` 最極端：3 張數字卡＋6 顆外框快捷鈕，換掉字就能當任何 SaaS 的後台首頁。

## Overall Impression

系統的**紀律**已經是這個規模裡的稀有物：顏色只有一處、對比度是量出來而不是宣稱的（390 個文字節點、0 個低於 AA，淺色深色皆然）、破壞性動作的文案具名具體並給了替代做法、查不到資料顯示「—」而不是 0。這些不是美化，是判斷力的證據。

最大的機會在**兩處被文檔承諾、卻沒被實作完的地方**，以及**簽名畫面缺了決策所需的那一欄**：派車看板的卡片沒有客戶名（派車的決策是「這台車跑哪幾家店」，而卡片上只有訂單號），shell 沒有登出也沒有身分／範圍顯示（多公司多部門正是這個產品的核心機制），以及 `PRODUCT.md` 的 24×24 命中區承諾只實作了 `<button>` 那一半。

## What's Working

1. **對比度與 token 紀律是量測得到的強項，不是宣稱。** 390 個可見文字節點、6 個路由、兩種主題，**0 個低於 AA**。成立的原因是可追的：顏色只存在 `index.css` 一處、元件只消費語意 token、深色是同一組值的覆寫。
2. **破壞性動作的確認範式＋錯誤訊息管線。** 五處確認都命名具體記錄、說明不可復原、給替代做法——「取消後不可復原，也不會退回待處理；如需重新出貨，請另開新單」是全站唯一把使用者的下一步寫進文案的地方。錯誤一律經 `error-message` 並優先採用後端 `details.reason`，`role="alert"`／`aria-busy`／`aria-invalid` 都到位。
3. **文案誠實。** 通知頁寫「未讀 4 筆（共 5 筆）」而不是騙人的「全部已讀」；首頁查詢失敗顯示 `—` 並說明「0 是真的沒有，兩者意義相反」；串流降級一定說出來。這條原則已被寫下、也被部分執行——第 3 項優先問題就是它沒被執行完的地方。

## Priority Issues

### 1. [P1] 派車看板：卡片沒有客戶、拖放沒有回饋、批次確認沒有確認

- **What**：`features/dispatch/pages/DispatchPage.tsx` 的卡片只輸出 `{o.orderNo}` ＋ 出貨日（指派後變成 `順位 N・{o.source}`，`W` 是裸代碼）；`cardAttrs()`／`dropTarget()` 沒有任何 drag-over 樣式（`dragging()` 只用來傳物件）；`批次確認派車` 按鈕直接呼叫 `confirmRoute`，標籤不帶筆數。
- **Why it matters**：派車的決策內容是「這台車要跑哪幾家店」，而卡片上唯一的識別是訂單號——調度員得逐張開詳情（開詳情會蓋住整個看板）或靠記憶把單號對應到店家。拖放時畫面完全不變，落點沒有指示；「拖到某張卡片前」與「拖到欄尾」是兩個不同意義卻看不出差別。放手後若再按批次確認，整欄的派車就在沒有確認、沒有筆數提示的情況下送出——而它會連動揀貨單與對點單。
- **Fix**：(a) 卡片加客戶名（`/orders` 已有 `customerNameById` 手法；正解是 `ListOrders` 直接回 `customer_name`／`route_name`，前端就不必自行 join）；(b) 來源走 `sourceLabelByCode`；(c) 用已有的 `dragging()` 上 `data-dragging`：來源卡 `opacity-50`、被 hover 的欄／卡片顯示主色落點線；(d) 按鈕標籤帶筆數（`批次確認派車（3）`）或走現成的 `useConfirm` 顯示「將確認 N 筆，其中 M 筆將產生重印」。
- **Suggested command**：`animate`（拖放狀態）＋ `clarify`（卡片內容與按鈕文案）

### 2. [P1] 沒有登出，也沒有「目前身分／公司／部門」的顯示

- **What**：`components/layout/Topbar.tsx` 只有 `SidebarTrigger` ＋ 頁面標題 `<p>` ＋ `ThemeSwitcher`；`features/account/AccountPage.tsx` 只有 `<PlanCard />`。全 repo 的 `登出|logout` 只命中稽核標籤表與 proto：**`AuthService.Logout` 沒有任何呼叫端**（已複查 grep）。`meQueryOptions` 只被 `BrandLogo` 與 `CompaniesPage` 用，而 `BrandLogo` 只把公司名放進 `<img alt>`。側欄頂端是產品名，不是公司名。
- **Why it matters**：這是一個用 session cookie 的後台，會放在倉庫或辦公室的共用桌機上；沒有登出＝使用者只能關分頁，而 cookie 還在。同時畫面上沒有任何地方說明「我現在看的是哪家公司、哪個部門」——而 `data_scope`（all/company/department/self）正是這個產品的核心機制。稽核日誌記得到 `logout`，形成前後端契約不對稱。
- **Fix**：頂列右側加帳號選單，由 `meQueryOptions` 顯示 `company.name` ＋ 角色正體中文標籤（需要時顯示目前 `data_scope`），內含「登出」呼叫 `AuthService.Logout` 後導向 `/login`。不需要新 RPC、新頁面。
- **Suggested command**：`shape`

### 3. [P2] 內部代碼外洩，且同一欄位在不同畫面有不同長相

- **What**（四處，live 驗證過）：`OrdersPage.tsx` 詳情對話框的 `<dd>{o.source}</dd>` 顯示 `W`（同筆在表格是「Web 中台」）；`EVENT_LABELS` 的鍵與後端實際值不符（後端送 `created`／`processing`，地圖只有 `create`），事件軌跡因此長出 `created`、`processing` 與「完成」「作廢」並列的半英文清單；`ReturnsPage.tsx:124` 客戶欄硬寫 `#{info.getValue()}` → `#88`／`#89`／`#90`，而同頁詳情框卻解析得出客戶名；`OrdersPage.tsx` 分切規格 `<option>` 直接拿 id 當標籤。
- **Why it matters**：這條原則專案自己寫下來了（`OrdersPage.tsx` 對來源欄的註解：「內部代碼不該出現在作業語言裡」），卻只在一處做到。退貨清單因此無法用客戶掃視，而那是審核佇列的首要資訊。
- **Fix**：映射收到資料邊界一層——(a) `EVENT_LABELS` 改用後端實際值，並為未知值留人類可讀 fallback（不要把 key 直接印出）；(b) 退貨清單沿用 `customerNameById`，或讓 `ListReturnRequests` 帶 `customer_name`；(c) 詳情框來源走 `sourceLabelByCode`；(d) 分切規格顯示規格名稱。四處都是一到三行的替換。
- **Suggested command**：`polish`

### 4. [P2] 權限矩陣：強調色泛濫、沒有批次操作、沒有未儲存提示

- **What**：`components/ui/checkbox.tsx` 未勾選態是 `size-4 rounded-sm border border-primary`（16px 方框配 6px 圓角，讀起來就是圓圈），`PermissionMatrix.tsx` 是 13×8＝104 格；`RolesPage.tsx` 的 `dirty` 只接到儲存鈕的 `disabled`。
- **Why it matters**：違反自家的 **One Accent Rule**（「主色在任一畫面不超過一成」）——那一頁只看得到橘色圈，順帶讓勾選框讀起來像 radio（它們是各自獨立的開關）；104 格沒有整列／整欄全選，調整一個動作的權限要點 13 次；改完 80 格後點側欄任一項目，草稿無聲消失。
- **Fix**：未勾選改 `border-border`（勾選仍 `bg-primary`），讓 104 格回到中性、主色只標示「已被授予」；表頭加每欄／每列全選；儲存鈕旁顯示「已變更 N 項」。
- **Suggested command**：`quieter`＋`distill`

### 5. [P2] 文件承諾的無障礙門檻有兩處實測未達

- **What**：
  - **命中區**：`index.css` 的覆蓋層選擇器是 `table thead button, table tbody button`。實測 `/printing` 列印歷史的「下載」是 `<a>`，**28×20**，六列各一個；首頁「檢視清單」的 `<Link>` 56×20；退貨頁照片連結同樣 20px 高。矩陣的勾選目標是 16×16。
  - **對比度**：選中列（`bg-muted`）上的「內建／啟用」Badge 是 **4.45:1**（白底列 4.82 通過）。
- **Why it matters**：`PRODUCT.md` 明文承諾「互動目標不分指標類型一律滿足 WCAG 2.5.8（24×24）」，`DESIGN.md` 也把 `::after` 覆蓋層寫成規則——實際只實作了按鈕那一半，而列印「下載」是每天都會用到的動作。第二項是 `DESIGN.md` Contrast-Carrying Rule 的直接違反（4.5:1 是硬要求），觸發條件還是常駐狀態。
- **Fix**：選擇器擴成 `table thead :is(button, a), table tbody :is(button, a)`；首頁卡片的 `<Link>` 補 `py-1` 或同法加覆蓋層；矩陣讓整個 `<td>` 成為點擊區。對比度：Badge 的 `/15` 疊 `bg-muted` 這一對沒被量過——把 `--info`／`--success` 的文字色調暗一階，或把 Badge 底色改為不透明（`bg-info/15` → 疊白後的實色）並重量測。
- **Suggested command**：`harden`

## Persona Red Flags

## Minor Observations

- **頁首 2px 分隔線**：20 個頁面都寫 `border-b-2 border-border`，但 `DESIGN.md` 的 Shapes 寫「邊框一律 1px」。全站一致所以讀起來像刻意——要嘛寫進文件，要嘛降回 1px。
- **`PageHeader` 被複製約 20 次**，首頁的 h1 因此漂移成產品名（其他 19 頁都是頁名），而頂列已經有一個 `<p>` 顯示頁名——首頁變成「側欄品牌名＝頂列頁名＝h1」三者不同調。
- **`--input` 等於 `--border`**（都是 `oklch(0.9220 0 0)`，對白底 1.26:1），表單邊界低於常被引用的 3:1；唯一消費 `border-input` 的是 `AnnouncementsPage` 手寫的四個欄位，它們同時繞過 `Input`／`Field`（40px／`rounded-lg`／`bg-card`），深色下會變成比卡片更暗的凹槽。調整一個 token、把原生控件覆蓋指向它，就能一次解掉對比與深色不一致。
- **`ListPagination` 是 16 個頁面共用的元件，卻住在 `features/users/components/`**。
- **分頁沒有每頁筆數選擇**；總數 ≤ 每頁筆數時整條分頁列不渲染，連「第 X–Y 筆」都沒有。
- **六條篩選帶都沒有「清除條件」**，且使用者頁的「公司關鍵字」單獨送出無效（實測：輸入「示範」後下拉縮到 2 項，按篩選後清單仍 8 筆、選值仍空）。
- **側欄沒有未讀角標、頂列沒有鈴**：`notifications_pb.d.ts` 為 `UnreadCount` 寫的註解是「通知鈴角標輪詢」，但 shell 完全沒實作。
- **看板欄寬不會撐滿**：`boardDensity` 只從 288px 降成 224px，四欄在 1180px 內容區只佔約 930px。
- **`prefers-reduced-motion` 全 repo 不存在**（已複查），而側欄寬度過場無條件執行 200ms。
- **`company_admin` 的降級提示是常駐的**：後端拒無部門身分訂閱串流，所以那不該被當成暫時狀態——文案選「不可用」是對的，但更誠實的做法是不對必然失敗的身分顯示重連訊息。
- **文件落後於程式**：`RolesPage.tsx` 註解寫「80 格 checkbox」（實際 104）；`AGENTS.md §6.3-1` 說 20 條路由未做 code-splitting，但 `router/index.tsx` 現在只剩 login／dashboard／403 是靜態 import。
- **空狀態很薄**：公告管理 0 筆時是 9 欄表格裡一行「尚無公告」，沒有指向「新增公告」；以「一頁一動作」的標準，空狀態正是該把主要動作再講一次的地方。
- **我沒能驗到的**：作廢流程（本租戶沒有 `completed` 訂單，最高風險的終態操作無法 live 走完）；深色模式的完整掃描（對比度陳述僅限淺色）；鍵盤／AT 語意的系統性檢查；列印輸出。

**Questions to Consider**

1. 派車看板的卡片該不該直接帶地址／配送區？只加客戶名或許仍不足以決定車次——這關係到 `ListOrders` 要不要回傳地址級欄位。
2. 「客戶名解析」目前是前端用下拉的已載入頁自行 join；當客戶數超過載入頁時會靜默退回 `#id`。**退貨清單的 `#90` 是否就是這個 fallback？** 若是，前端 join 就不是可接受的長期做法。
3. 真實使用者會同時屬於多個公司／部門嗎？若是，shell 需要的是**範圍切換器**而不只是顯示。
4. 登出是刻意留給 IdP／App 嗎？若是，`AuthService.Logout` 與稽核日誌的 `logout` 標籤要如何在產品層交代？
