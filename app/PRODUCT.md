## Users

- **業務**（主要）：在客戶店家現場用手機開單。自行決定品名用打的或從清單選；維護該客戶的專屬商品清單；挑選偏好送貨日；審核客戶發起的退貨。
- **客戶店家 — 主帳號**：只管管理、不業務登入。自助建立／停用／重置子帳號（self 範圍），可改自己的密碼。主帳號不可自停，後台停用會連鎖子帳號。
- **客戶店家 — 子帳號**：唯一的店家業務身分。看自己的訂單歷史、發起退貨、接收通知；員工首次接觸時以 QR 深層連結登入。
- **客戶店家 — 業務子帳號**：建立客戶時自動附帶，專供該客戶的主責業務登入代客操作；店家端灰化不可管理（沒有密碼就無法登入）。
- **guest（員工未完成註冊）**：OIDC 登入後待審核，審核完成前不建帳號；App 不服務這個狀態。

## Product Purpose

多公司訂出貨系統的現場端：讓業務不必回辦公室，就能在店家現場完成開單、改名與指定送貨日；讓店家自己管理子帳號、查看訂單、發起退貨並收到結果。

後台（派車、單據列印、主檔維護）見 `../frontend/PRODUCT.md`；平台維運見 `../platform-console/PRODUCT.md`；產品整體（含 SaaS 化的商業形態與成功定義）以 repo 根 `../PRODUCT.md` 為準。本檔只記現場端這一面。

現場端的成功定義：一筆訂單從走進店家到送出，不需要離開手機、不需要紙本、不需要回辦公室補資料；店家對自己的帳號與退貨也能在同一個 App 內閉環。

## Positioning

部門自治主檔 + 雙層租戶防護（OpenFGA 管功能、PostgreSQL RLS 管資料範圍）的產品在店家現場的介面。相鄰產品做不到的：同一商品可在不同部門、不同客戶各自命名，不需跨部門大總表；業務資料域全系統不儲存金額。

現場端獨有的機制是**身分經濟**：主帳號只管人、子帳號才做事、業務子帳號是業務的代理身分——三種帳號在同一支手機上各自看到不同的世界，且店家不必理解權限模型。

## Operating Context

- 業務在店家現場作業，App 是唯一的現場工具；派車與四種紙本單據列印都在後台。
- 手機常在單手持握、光線不理想的店內使用；主要動作必須在單手可及的範圍內完成。
- 專屬商品清單的刪除語意是作業慣例：偶爾不用的品項把數量設 0 保留（不再顯示於單據），長期不用才刪除（不再帶出）。
- 偏好送貨日為週一至週六核取；非勾選日下單自動順延。日期的計算是 UTC+8 的日曆天。
- 訂單狀態機在現場端只有兩個動作：待處理可取消、處理中可完成；完成之後的作廢留在後台。
- 退貨流程：客戶發起（從歷史訂單挑品項，或從專屬商品清單帶入）→ 業務審核（駁回必填原因）→ 通過後可出示退貨證明。退貨申請只收客戶子帳號身分，主帳號不能建單。
- 通知是工作流的一部分（FCM + 站內，**無 Email**）：業務下單推客戶子帳號、後台新增專屬商品推主責業務、退貨審核結果推發起帳號；促銷推播依分類標籤選群，與公告分離。公告在 App 首頁（banner + 圖文），與通知分屬兩個入口。
- 店家以主帳號自助管理子帳號（self 範圍）；管理端保留移交與救援路徑。
- QR 登入是店家的第一哩路：管理端（或 App 內的帳號頁）產生 QR／深層連結，子帳號點開即進入選擇帳號並登入。
- 介面語言為繁體中文（`zh-Hant`）；文件、註解、commit message 一律繁體中文；多語 UI 不在範圍。
- 既有 UI 設計稿在 Pixso（`多公司訂出貨系統` UI 稿的 App 六畫面；來源存檔 `docs/design/2026-09-18-pixso-版面美化-進度存檔.md`）。

## Capabilities and Constraints

現場端的功能面：

- **登入與身分**：身分選擇（店家／業務）；店家以帳號密碼或 QR 深層連結（列出可選子帳號）進入；業務以 OIDC 或帳密進入。首登強制改密碼（臨時密碼有時效）。
- **現場開單**：品名可手打或自清單挑選；手打的品名可綁定成該客戶的別名；可從客戶專屬商品清單帶入；指定偏好送貨日；也能在 App 內以手動表單新增客戶（主檔 + 登入帳號），不需要回後台。
- **專屬商品清單**：業務可新增、改名、設數量、設 0 保留、刪除，並以查詢方式挑產品。
- **訂單**：清單（分頁＋狀態篩選）、明細與事件軌跡、取消（待處理）、完成（處理中）。
- **退貨**：清單（狀態篩選）、建單（挑訂單 → 勾品項 → 數量 ＋ 必填原因 ＋ 備註）、詳情（審核核准／駁回、退貨證明）。
- **通知與公告**：通知清單（全部／未讀、點擊標記已讀、未讀徽章）、公告首頁（banner 輪播、最新消息與圖文文章）。
- **帳號管理（主帳號）**：列出子帳號（含系統預設的業務子帳號灰化不可管理）、建立子帳號（一次性顯示臨時密碼）、重置密碼、停用；改自己的密碼。
- **深層連結**：`customer_account_qrcode/*`（QR 登入）與 `customer_account_manage`（帳號管理登入）以 Universal Links / App Links 承接；`salesorder://` 自訂 scheme 只用於 OIDC 回呼。

約束與硬規則：

- **業務資料域不儲存金額**：App 的訂單、商品、專屬商品畫面都沒有價格欄位，也不得為了顯示而新增。
- 認證：App 用 access JWT 1 小時 + refresh 30 天旋轉；停用／強制登出／改密碼／角色變更以 `token_version` 全數失效。店家子帳號另有 QR Code 登入。
- 通知失敗只標記失敗、不重試（重試佇列不在範圍）；App 強制更新、多語 UI、上傳病毒掃描皆不在範圍。
- 工程約束：一律以 `fvm` 執行；雙 flavor（dev / prod）＋ `--dart-define` 注入組態；`salesorder://` 或深層連結路徑的異動必須同步 AndroidManifest、Info.plist 與 AuthConfig；不新增相依套件除非現有套件明確不足。
- 1.1 是獨立迭代（拍照建客戶、語音下單，`docs/superpowers/specs/2026-07-18-app-ai-assist-1.1-design.md`），不得混入 1.0 範圍。
- 錯誤顯示一律經 `core/error_info.dart` 的 `localizedErrorMessage`：優先後端 `ErrorInfo` 的 `details['reason']`（若含中文）與碼表樣板，再退回連線層文案；各頁不得自建 `connect` 碼 → 訊息對照表（同一個 connect 碼在不同路徑是不同原因，硬編必然誤譯），頁面專屬覆寫只保留該頁獨有的成因。

## Brand Commitments

- 現場端是工具而非品牌介面：外觀跟隨平台習慣（Cupertino / Material），不另立品牌主題、不自帶字型。
- 用語沿用現場慣稱（開單、派車、揀貨、對點、分切、車次、送貨日），不為了「產品感」改寫作業詞彙。
- 對店家的訊息一律直述其結果（審核通過／不通過與原因），不用技術詞（scope、權限、token）。

## Product Principles

1. **現場優先**：業務在店家現場就能完成開單與改名，不要求回辦公室補資料；能單手完成的主要動作不藏在二層選單。
2. **店家自助、後台有逃生門**：子帳號由店家自己管（self 範圍），管理端保留移交與救援路徑。
3. **通知是工作流的一部分**：推播路由（誰下單推給誰、審核結果推給誰）是產品行為，不是附帶功能。
4. **身分不同，世界不同**：主帳號、子帳號、業務子帳號各自只看到自己的事；店家的操作不得因為權限模型而多出理解負擔。
5. **不持有金額**：系統刻意不儲存價格，App 也不得為了顯示而新增。

## Accessibility & Inclusion

- 全站繁體中文（`zh-Hant`）；多語 UI 不在範圍。
- 現場使用情境：單手持握、光線不佳、可能戴手套；主要動作的觸控目標不得小於平台建議值，狀態不得只靠顏色承載。
- 控件必須跟隨平台語彙（iOS 用 Cupertino 習慣、Android 用 Material 習慣），使用者不需重新學習系統行為。
- 時間欄位一律以**營業時區（UTC+8）**顯示（`lib/ui/format.dart`）：後端各服務對同一個瞬間的序列化偏移不一致（部分 `.UTC()`、部分伺服器本地），切字串會讓同一個瞬間在 Web 與 App 之間相差八小時。純日曆日欄位（`expectedDeliveryDate`）不經時區換算。
