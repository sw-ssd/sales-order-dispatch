## Platform

web

## Users

- **部門管理員 / 公司管理員 / 總管理員**（主要）：桌機後台。建立與維護各自部門的主檔（客戶、商品、業務、倉別、車次、分切規格、商品分類、字典），管理部門人員帳號與角色權限，執行派車與單據列印。公司管理員僅限自己公司，總管理員可跨部門調閱全部資料。
- **一般職員（含會計）**：桌機後台。日常開單、訂單異動、查詢與列印，以及公告管理。
- **業務**：以 App 在店家現場作業（見 `../app/PRODUCT.md`），在後台檢視自己部門的訂單與派車狀態。
- **客戶店家**：只在 App 出現，後台沒有客戶介面——唯二的例外是 QR 深層連結的落地頁與子帳號管理頁（`/customer_account_qrcode/*`、`/customer_account_manage`），兩者皆不套後台外框、不需後台登入。
- **平台營運人員**：不使用本 SPA；平台維運走獨立主控台（見 `../platform-console/PRODUCT.md`）。租戶 SPA 不掛任何 `platform.*` 能力或平台路由。

## Product Purpose

多公司訂出貨系統的桌機中台：讓多個部門各自擁有客戶、商品與庫別主檔，業務在店家現場開單，中台完成派車與四種紙本單據列印，並以 FCM + 站內通知串連業務、店家與管理端。

產品整體（含 SaaS 化的商業形態、上線方式與成功定義）以 repo 根 `../PRODUCT.md` 為準。本檔只記中台這一端的事。

存在的理由：取代客戶既有的三倉系統（`sales-order-backend` / `-frontend` / `-app`）。不遷移舊資料、以 Big Bang 完成既有客戶切換；舊系統的程式碼僅供背景參考，不沿用。

中台在切換後的成功定義：日常作業（開單 → 派車 → 揀貨 → 列印 → 送達）完全不依賴舊系統，且各部門的主檔與資料互不干擾；同時中台要能顯示自己公司的訂閱狀態與權益投影，讓「方案不含某功能」與「還沒訂閱」在畫面上可辨識。

## Positioning

部門自治主檔 + 雙層租戶防護：功能權限由 OpenFGA 管（資源級 userset），資料範圍由 PostgreSQL RLS 管（`data_scope` = all / company / department / self），兩者都不依角色名稱判斷。

相鄰產品做不到的機制：同一商品可在不同部門有不同名稱，又可在各部門的不同客戶各自改名綁定，且**不需要跨部門大總表**。另：業務資料域全系統不儲存金額。

## Operating Context

- 派車看板是 Kanban 拖放 + 車次批次確認；拖放比對 `version` 樂觀鎖，`WatchBoard`（Connect server streaming）只觸發全量重查，跨 replica 走 Valkey pub/sub，串流不可用時降級為輪詢。
- 四種單據是實際作業文件：單車總表、車次對點單、揀貨單（依車次 → 倉別 → 分類 → 品名排序）、加工單（加工室揀／配送揀兩區塊；加工後數量列印空白、手寫回填，不回寫）。重印開放 dept_admin / staff，必填原因。
- 稽核日誌與業務操作同一 DB 交易寫入（同成功同失敗）；保留期由管理頁設定 1 / 3 / 6 / 12 個月或永久。日期、動作、資源可篩選，並可展開變更快照。
- 公告與通知都在中台：公告管理（CMS）與通知中心（本人清單、未讀數、狀態與通道篩選、單列與整頁標記已讀）分屬兩個入口；促銷推播依分類標籤選群，與公告分離。
- 訂單與明細的作業慣例：手打品名可綁定成該客戶的別名；下單可就客戶專屬商品清單帶入；偏好送貨日為週一至週六核取，非勾選日自動順延。
- 中台是桌機工作環境（側邊欄 + 可拖寬的內容區），但版面同時要能收斂為抽屜式導覽以應付較窄視窗。
- 介面語言為繁體中文（`zh-Hant`）；文件、註解、commit message 一律繁體中文；多語 UI 不在範圍。
- 設計 token、元件庫與深色模式由中台提供，並被平台營運主控台以別名共用。

## Capabilities and Constraints

- 路由即功能地圖：首頁（今日待出貨／待處理／處理中的統計卡 + 公告看板 + 快速連結）、客戶總表、商品總表、訂單管理、退貨管理、派車規劃、單據列印、公告管理、四種主檔（車次／倉別／商品分類／分切規格）、通知中心、稽核日誌、公司／部門／角色權限／使用者四頁管理，以及帳號／方案頁。
- 授權在後端的 OpenFGA + RLS；前端只做兩件事：路由 `beforeLoad` 的能力守衛（失敗導向 `/403`）與顯示開關。前端守衛只影響體驗，不構成授權。
- 認證：OIDC（IdP 不限 Google）與帳密兩條路並存；員工可用 Google Workspace OIDC，亦可用帳密。Web 用 scs + Valkey session cookie；停用／強制登出／改密碼／角色變更以 `token_version` 全數失效。
- 角色：`super` / `company_admin` / `dept_admin` / `staff`（兼會計）/ `customer` / `guest` / `developer`；7 個內建角色 + `role_permissions` seed，後台可調、防鎖死。
- 訂單狀態機：`pending ⇄ processing → completed`、`cancelled`、作廢 `voided`（終態）；所有異動寫 `sales_order_events`。
- **業務資料域不儲存金額**（訂單、明細、商品、客戶專屬商品皆無金額欄位）；金額只存在於平台計費域，中台的帳號／方案頁顯示的是訂閱與權益投影，不是帳務資料。
- API：Connect-RPC 為唯一來源（proto 產生型別）；REST 只保留公開端點（版本、OIDC、QR 兌換、檔案、公司公開資訊）。錯誤訊息一律經 `lib/error-message.ts`：優先用後端 `ErrorInfo` 的結構化內容（含 `details.reason` 這類可行動原因），其次碼表文案，且不得把錯誤碼本身顯示給使用者。
- 統一軟刪除（`deleted_at` + 部分唯一索引）；編號取號與建檔同一交易（樂觀鎖）。
- 主檔與訂單的建檔／編輯組裝在同一個交易內完成（守衛、明細驗證、單位換算、送貨日順延、取號）。
- 檔案本地儲存，白名單（jpeg / png / webp ≤5MB、PDF ≤10MB）+ magic bytes 雙重檢查；檔案沒有獨立頁面，皆由 owner 入口進出（公司 logo、列印 PDF）。
- 訂閱狀態與權益：權益快照「尚未訂閱」時回傳空的使用量清單，前端據此區分「方案不含」。席位值語意：0 = 不含、-1 = 不限、>0 = 上限。
- 明確不在範圍：供應商退貨授權、獨立報價單、簽核流程、進銷存庫存、配送專屬頁、獨立會計角色、自建 IdP、Cmd+K 全域搜尋、電子發票開立、App 強制更新、通知重試佇列、上傳病毒掃描、多語 UI。
- 未定案：Noto Sans CJK TC 生產字體授權與安裝方式（上線前必答）。

## Brand Commitments

- 名稱「多公司訂出貨系統」；中台沒有對外行銷素材，也沒有品牌 logo（公司 logo 是租戶自己的資料）。
- 用語沿用現場慣稱（派車、揀貨、對點、分切、車次），不為了「產品感」改寫作業詞彙。
- 資料密度優先：中台是每天使用的工具，不是展示品；表格與表單的緊湊度是刻意選擇。

## Product Principles

1. **部門是主檔的邊界**：客戶、商品、庫別、車次由各部門自建，不做跨部門大總表；跨部門調閱是例外而非常態。
2. **權限與資料範圍分離**：功能（OpenFGA）與資料可見範圍（RLS `data_scope`）各自判斷，不綁角色名稱。
3. **紙本是交付介面**：四種單據的欄位、排序與留白是作業需求，不是裝飾；列印相關的調整不得為了畫面好看而動順序。
4. **不持有金額**：中台不引入價格欄位；訂閱與權益是狀態投影，不是帳務帳本。
5. **一頁一動作**：每個作業頁面同時只有一個主要動作，其餘是次要或唯讀——工作人員在趕單時不該分辨優先順序。

## Accessibility & Inclusion

- 全站繁體中文並標記 `zh-Hant`。
- 深色模式是既有基線：語意 token 同時提供淺／深兩套，預設值可為跟隨系統；表單控件在深色下必須可辨識，載入時不得閃爍（anti-FOUC）。
- 表格與狀態不得只靠顏色承載：狀態一律有文字，顏色只是加速判讀。
- 觸控與滑鼠都要可用；窄視窗下側邊欄收斂為抽屜。密集表格以橫向捲動（不換行）保住列高與欄位對齊，因此窄視窗的重點是**讓捲動可被發現**（捲軸、邊緣提示），而不是消除捲動。
- 時間一律以**營業時區（UTC+8）**顯示：後端各服務對同一個瞬間的序列化偏移不一致（部分 `.UTC()`、部分伺服器本地），前端必須自行轉換而非裁切字串，否則同一瞬間會因頁面而異、也隨部署機器而異。純日曆日欄位不轉換。
- 互動目標不分指標類型一律滿足 WCAG 2.5.8（24×24 CSS px）：表格行內文字動作的命中區以覆蓋層垂直擴張補足，滑鼠與觸控皆適用。
