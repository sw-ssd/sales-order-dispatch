# App AI 輔助功能 1.1 設計備忘錄（拍照建客戶 / 語音下訂單）

> 版本：**v0.3.1（草案）**
> 母規格：`2026-07-16-sales-order-1.0-design.md` v1.0.24（以下稱「1.0 規格」，引用以 § 標記）
> 定位：**1.1 獨立迭代**，不影響 1.0 Big Bang 上線範圍（1.0 規格 §13）。

---

## 1. 背景與範圍

- 需求來源：業務端新需求「App 新增以拍照或上傳照片新增客戶、業務語音下訂單」（2026-07-18 討論定案）。
- 兩個功能：
  - **A. 拍照/上傳照片新增客戶**：拍名片/招牌 → LLM vision 辨識 → 預填建檔表單 → 人工確認 → 建檔。
  - **B. 業務語音下訂單**：口述 → 雲端 STT → LLM 解析品項 → 訂單草稿 → 人工確認 → 送出。
- 已定案決策（2026-07-18）：
  1. 版本歸屬：**1.1 獨立迭代**（1.0 範圍維持鎖定）。
  2. OCR 路線：**LLM vision**（多模態模型直接輸出結構化欄位）。
  3. 語音路線：**雲端 STT + LLM 解析**（辨識率優先，含台灣國語/台語腔適應）。
  4. App 建客戶範圍：**客戶主檔 + 登入帳號**（主帳號轉交店家、業務子帳號業務留存；臨時密碼照 1.0 規格 §4.2，業務當場交付）。
  5. （2026-07-18 追加）**App 手動表單新增客戶（主檔 + 登入帳號）提前納入 1.0**（規格 v1.0.26，§4.2 / §9.4）；登入帳號編碼 = **公司定義前綴 + 自增 ID**。1.1 僅保留拍照/上傳照片的 AI 預填輔助與語音下單。

---

## 2. 共同原則（不可妥協）

- **AI 僅預填，一律人工確認後才建檔/送單**；禁止 AI 自動提交。
- **降級路徑**：辨識失敗、逾時或信心不足時，無痛退回純手動輸入，不阻塞業務流程。
- **業務規則不繞道**：單位換算、取號、偏好送貨日順延皆走 1.0 規格 §6.2–6.5 既有邏輯（1.0 全系統不儲存金額，v1.0.28 起，AI 僅填品項與數量草稿）；AI 只負責填草稿。
- **稽核**：凡經 AI 輔助產生的資料，於 `audit_logs` 與訂單欄位標記來源，供事後追查。
- **個資與資料外送**：名片影像、語音音訊、客戶報價資料將送第三方雲端（STT / LLM），1.0 規格 §14.1 需補第三方資料處理協議（DPA）與當事人告知。
- **成本控管**：AI 端點納入 rate limit（1.0 規格 §14.3），設每使用者每日次數上限。

## 3. 功能 A：拍照/上傳照片新增客戶

### 3.1 前置條件

1.0 規格 v1.0.26 起，App 端已具備**手動表單新增客戶**（主檔 + 登入帳號，帳號 = 公司定義前綴 + 自增 ID，見 1.0 規格 §4.2、§9.4）。1.1 僅在既有建檔流程上新增「拍照 / 相簿上傳」的 AI 預填入口，不重複建置建檔功能。

- 角色：`staff` / `dept_admin`，沿用 `role_permissions` 既有 `customer:create` 權限，不新增權限項。
- 拍照僅為預填手段：辨識後進入與手動建檔相同的表單確認頁；無照片情境直接走 1.0 手動流程。

### 3.2 流程

1. 業務於 App 新增客戶頁（1.0 已建置）選「拍照」/「相簿上傳」；或直接手動輸入（1.0 既有流程）。
2. 照片經既有檔案上傳端點上傳（1.0 規格 §14.3 白名單已涵蓋 `image/jpeg` / `image/png` / `image/webp` ≤ 5 MB，無需擴充）。
3. 後端呼叫 LLM vision，回傳結構化欄位：店名、統一編號、電話（可多筆）、送貨地址、帳單地址、聯絡人姓名/職稱。
4. 預填建檔表單 → 業務確認並補齊 AI 無法辨識的必填欄位（付款方式、結帳方式、客戶類型、發票類型、預設負責業務等，對應 1.0 規格 §5.2 `customers` 欄位）。
5. 送出後後端於同一交易建立：
   - `customers`（+ `customer_addresses`、`customer_contacts`）
   - `users` 客戶登入帳號：`customer_code` 依 1.0 規格 §4.2 自動產生（公司定義前綴 + 自增 ID，建立後不可修改）；臨時密碼照 §4.2（24 小時效期、首登強制修改），App 當場顯示一次供業務轉交客戶。
6. 照片留存為 `file_assets`（`owner_type = customer`），供日後查核；建檔時可選擇不留存。

### 3.3 錯誤與降級

- LLM 呼叫失敗 / 逾時 / 回傳不可解析 → 直接進手動表單；已上傳照片仍可選擇留存。
- 統編、電話格式於確認頁本地校驗，不依賴 AI 輸出正確性。
- LLM 原始回應不留存（個資最小化）；稽核以「人工確認後的建檔內容」為準。

### 3.4 稽核

- `audit_logs`：`action = create`、`resource_type = customer`，payload 標記 `via = photo_assist`（純手動為 `manual`）。

## 4. 功能 B：業務語音下訂單

### 4.1 範圍

- 僅業務（`staff` / `dept_admin`）使用；客戶端流程不變（1.0 規格 §9.5）。
- 入口：App 快速下單流程（§9.4）內提供「語音輸入」。

### 4.2 流程（分兩階段）

**階段一（1.1 MVP）**：

1. 業務**先選客戶**（上下文最準，只需帶該客戶的 `customer_products`）。
2. 按住錄音 → 音訊上傳 → 雲端 STT（zh-TW）→ 文字。
3. 文字 + 該客戶 `customer_products`（別名、預設數量、專屬單價、預設切法）送 LLM function calling → 品項草稿陣列（品名 / 數量 / 單位 / 分切規格 / 特殊切法備註 / 預計出貨日）。
4. 訂單草稿確認頁：每行可改、可刪、可手動加行；單價依 1.0 規格 §6.3 帶入。
5. 確認送出 → 走 1.0 規格 §6.2 既有下單流程（取號、訂單通知皆不變；1.0 不涉及金額）。

**階段二（1.1 後期評估）**：免選客戶 — 語音內容含客戶名稱，以部門客戶清單為上下文比對客戶；需評估上下文 token 成本與誤判率，另行定案。

### 4.3 資料與欄位

- `sales_orders` 新增 `entry_method` 欄位（`manual` / `voice`，預設 `manual`；1.1 migration 新增）。
- 訂單編號來源碼維持 `A`（App），**不改** 1.0 規格 §6.5 編碼規則。
- 音訊檔案**預設不留存**：STT 完成後即刪（個資最小化）；STT 文字與 LLM 解析結果摘要寫入 `sales_order_events.payload` 供稽核。

### 4.4 降級與錯誤處理

- STT 失敗 / 無語音輸入 → 提示後回到手動下單。
- 品項無法比對（別名找不到）→ 該行標記「待確認」，由業務手動選品，不整單失敗。
- 數量/單位模糊（如「來一點」）→ 以該品項 `default_qty` 預填並標記，由業務確認。

### 4.5 上傳與限流

- 1.0 規格 §14.3 白名單需擴充音訊：`audio/mp4`（m4a）、`audio/mpeg`、`audio/wav`、`audio/webm`，≤ 10 MB，單次錄音 ≤ 60 秒。
- Rate limit：每使用者每日語音解析次數上限（建議 100 次，後端可配置），防止成本失控。

### 4.6 供應商選型（待辦）

- 候選組合：GCP Speech-to-Text + Gemini / OpenAI Whisper + GPT function calling / Azure Speech + Azure OpenAI。
- 評估維度：zh-TW 辨識率（含台語腔與食品/分切術語）、端到端延遲、每分鐘成本、DPA 條款、資料落地區域。
- 驗收門檻：以真實語料 POC（名片 20 張、語音 20 句），辨識正確率未達門檻則重新選型或調整方案。
