## Platform

web

## Users

- **平台營運人員（operator，主要且唯一的使用者）**：產品方自家的營運／支援同仁，日常工作就是這個工具。以自有 OIDC 登入（`platform.operators` 白名單，後端每次請求都回查）進入，**不需要也不得持有任何租戶公司的 `users` 列**。未來可能開放給特定客戶的專責人員協助管理自己的租戶。
- **本工具的訪客=無。** 租戶公司的人（super / company_admin / dept_admin / staff / 業務 / 店家）永遠不進這個工具；他們看到的是租戶 SPA（`../frontend/PRODUCT.md`）與 App（`../app/PRODUCT.md`）。

## Product Purpose

平台方的內部營運主控台：在不動用租戶身分的前提下，維運整個 SaaS 平台。

實際要完成的事：看租戶清單與單一租戶的訂閱狀態、為特定租戶開例外（override）、維護方案與價目、檢視方案權益矩陣、追蹤待收款並記錄收款、查詢平台稽核軌跡。

存在的理由：租戶 `super` 帳號是逃生門而非日常維運途徑（平台操作不得混入租戶身分，稽核 actor 也不同）；因此平台維運需要一個自有登入、自有邊界、自有稽核的介面。工具與租戶 SPA **邏輯分離**：只走 `platform/v1`，不碰租戶 API。

成功定義：營運人員不必求助工程師，就能完成租戶狀態判讀、例外開立、價目調整、收款登記與事後追溯。

## Positioning

「**只走平台 API，且不與租戶端共用身分、路由與守衛**」的內部工具：主控台自己的路由樹、自己的登入守衛、自己的 session 探針；與租戶 SPA 只共用 UI 元件庫與設計 token。前端守衛只是體驗，後端 operator 中介層才是唯一決策者——繞過前端拿不到任何跨租戶資料。

## Operating Context

- 這是**內部工具**：使用者少、權限高、沒有 onboarding 任務，也沒有行銷或自我推銷的必要；`<meta name="robots" content="noindex">`。
- 使用場景是營運排障與帳務作業，常與客服對話同時進行：需要「一眼判斷這個租戶現在發生什麼事」，而不是逐頁翻找。
- 六頁構成完整動線：租戶列表 → 租戶詳情（訂閱與例外）→ 方案價目／權益矩陣（理解某租戶為什麼看不到某功能）→ 待收款（實際收錢）→ 稽核（事後追溯）。前三者是「判讀」，第四者是「寫入」，最後者是「查證」。
- 需要登入才能做事；未登入一律導向登入頁。登入就是一次跳轉到後端 OIDC 端點，沒有帳密表單。
- 平台維運與租戶業務**不共用身分與稽核**：這裡每個寫入都是平台稽核紀錄，actor 是 operator。
- 已知邊界（產品事實，不是缺陷清單）：v1 沒有登出端點，前端只能清本地狀態；console 必須與 API 同 origin；部分計費生命週期操作與 operator 管理目前只有後端能力、沒有 UI。

## Capabilities and Constraints

已落地的能力（六頁）：

- **租戶列表**：搜尋與分頁；狀態一眼可辨。
- **租戶詳情**：訂閱狀態、方案、席位、試用與寬限期、用量；可**建立例外（override）**覆寫個別租戶的權益——這是本工具最關鍵的寫入動作。
- **方案與價目**：檢視方案階梯；可**調價**（月繳／年繳價目與年繳折扣）。
- **方案權益矩陣**：唯讀對照「哪個方案含哪些功能與上限」，用來解釋租戶端為何看不到某功能。
- **待收款**：逾期未收的租戶期別清單；可**記收款**（記錄收款人、金額、備註）。
- **平台稽核**：以起迄日、動作、資源篩選平台寫入軌跡。

寫入的共通規則：都在對話框內完成、都必須填**原因**（進稽核）、都用明確動詞的確認按鈕；不使用瀏覽器原生 confirm。

邊界與硬規則：

- 只走 `platform/v1`（`PlatformAdminService`）；不得引入租戶 API 或租戶端路由與守衛。
- 平台能力命名空間（`platform.*`）永不出現在租戶 `GetAbility` 與租戶角色權限矩陣。
- 錯誤顯示一律走共用錯誤碼表（`ErrorInfo.code` + 已渲染訊息），不硬編訊息字串。
- 前端產生的 proto 與錯誤碼檔不可手改。
- 明確不在範圍：跨來源部署、自助登出、operator 帳號自助管理、金流與電子發票自動化（後續 adapter）、代租戶執行業務操作。

## Brand Commitments

- 名稱「平台營運主控台」；介面語言繁體中文（`zh-Hant`）。
- 語氣是**內部工具**：直述、術語化、可用營運專有名詞（租戶、方案階梯、席位、寬限期、例外、待收款），不為了親切而改寫。
- 沿用租戶 Web 的設計 token 與元件庫，因此視覺上與租戶 SPA 同源——差異只在資訊與密度，不在風格。

## Product Principles

1. **營運身分與租戶身分不混用**：這裡的每個動作都是平台動作，落平台稽核；需要改租戶資料時走平台 API，不借用租戶帳號。
2. **判讀先於操作**：預設畫面是「這個租戶現在的狀態」，寫入動作是收斂在詳情頁與待收款頁的例外處置。
3. **寫入必留原因**：任何改變租戶權益或帳務的動作都必須能被事後追溯。
4. **與租戶端同源不同界**：共用 UI 元件與 token，但不共用路由、守衛、session 或 API。
5. **不取代租戶的工具**：這裡不做租戶的業務操作（派車、開單、列印），那些是租戶端與 App 的工作。

## Accessibility & Inclusion

- 全站繁體中文並標記 `zh-Hant`，供螢幕閱讀器正確朗讀。
- 高資訊密度表格（租戶、權益矩陣、待收款、稽核）必須有可用的頁籤順序與可辨識的狀態文字；狀態不得只靠顏色（顏色用於加速判讀，文字才是真相）。
- 跟隨租戶 Web 的深色模式基線與語意 token；表單控件在深色下必須可辨識。
